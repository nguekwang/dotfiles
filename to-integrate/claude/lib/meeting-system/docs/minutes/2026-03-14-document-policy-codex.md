- Objective: 作成するドキュメントの標準ルールを決め、読みやすさと解釈しやすさを高める

## Agenda

- ドキュメント構造の標準ルールを整理する
- 記述ルールと表記ルールの統一方針を決める
- 論点、未決事項、TODO の分離方法を決める

## Current Focus

- 忙しい読者でも冒頭だけで目的と要点を把握できる文書標準の確立

## Summary

今回の会議では、ドキュメント標準の最重要要件を「忙しい読者が冒頭だけで文書の目的と要点を理解できること」と定義した。そのため、すべての文書で本文より前に `Purpose` と `Summary` を置く方針を決めた。

その上で、文書全体は結論ファーストかつ階層的に構成し、ピラミッドライティングを基本、PREP法は段落単位の補助として扱う方針で整理した。また、`Decisions`, `Open Questions`, `Action Items` を分離し、表記は Markdown ベースで統一する方向で合意した。

## Context

ユーザーは会議モードでの進行を指定し、会議名を `document-policy`、目的を「作成するドキュメントのルールを決定する」、背景を「ドキュメント内の文章の構造が統一されておらず、人間にとってもAIにとっても分かりづらい」、制約を「MECEかつ階層的に、人間の思考にとって自然な構造で書くこと」、決めたいことを「論点、TODO の整理」とした。

進め方として、役割別の発言、ランニングメモの維持、脱線時の `Parking Lot` 退避、`Current Focus` の明示、最後に `Decisions`, `Open Questions`, `Action Items` を出すことが求められた。会議の途中で、ユーザーから「最初にそのドキュメントの目的と要旨を書くようにしてほしい。忙しいため」と追加要望があり、冒頭要件の必須化が論点として追加された。

## Discussion

### User

- ドキュメント内の文章構造が統一されておらず、人間にもAIにも分かりづらいという課題がある。
- 文書は MECE かつ階層的で、人間の思考にとって自然な構造にしたい。
- ピラミッドライティング、結論ファースト、PREP法、Markdown、記号の表記ゆれ解消、時系列整理などを含めてルール化したい。
- 論点整理と TODO 整理を決めたい。
- 忙しい読者でもすぐ読めるように、文書の最初に目的と要旨を書くことを強く求めた。

### PM

- 目的は「読みやすい文書」一般ではなく、誰が書いても同じ骨格になり、人間にもAIにも解釈しやすい標準を作ることだと整理した。
- 論点は `構造 / 記述 / 表記 / 運用` の4分類に分けるのがよいと整理した。
- 最優先で読むべき情報が冒頭にない文書は、忙しい前提の運用に合わないため、冒頭要件を必須にすべきとした。
- 文書種別ごとの差分は将来的に許容できるが、まずは全体共通ルールを定めるべきとした。

### Dev

- AI利用も前提なら、曖昧さを減らし、「何の話か」「結論は何か」「根拠は何か」「次に何をするか」を分離した構造が必要と整理した。
- 見出し粒度の不統一、結論と背景の混在、TODO と検討事項の混在、時系列と論理構造の混在、記号や用語の揺れが主な問題として挙がった。
- 文書全体はピラミッド構造を優先し、PREP法は段落単位の補助として使うのが妥当とした。
- 冒頭に `Purpose` と `Summary` を固定で置くと、人間にもAIにも後続構造の解釈が安定すると整理した。

### Ops

- ルールが厳密すぎると定着しないため、必須ルールは最小限に絞るべきとした。
- 共通テンプレートの必須項目候補として `Purpose`, `Summary`, `Details`, `Open Questions`, `Action Items` が挙がった。
- 時系列記述は履歴や障害報告などの例外用途に限定し、通常文書では論点別整理を原則にすべきとした。
- 忙しい読者向けには、毎回同じ順序の固定フォーマットが重要だと整理した。

### Reviewer

- レビューしやすい文書の条件として、「1つの見出しに1つの主張」「上位見出しは下位見出しをMECEに束ねる」「結論先出し」「事実・解釈・依頼の分離」「未確定事項の明示」を提示した。
- PREP法は段落単位では有効だが、文書全体の構造ルールとしてはピラミッドライティングを優先すべきとした。
- `Purpose` と `Summary` があれば、文書の価値を最初の短時間で判定できるため、レビュー観点としても有効だと整理した。
- `Decisions`, `Open Questions`, `Action Items` を分けることで、決定事項と未決事項の混線を防げるとした。

## Decisions

- すべての文書は冒頭に `Purpose` を書く。
- すべての文書は冒頭に `Summary` を書く。
- `Purpose` と `Summary` は本文より前、文書の先頭に置く。
- 文書の最低ラインの構造は `Purpose -> Summary -> 本文` とする。
- 文書全体は結論ファーストで書く。
- 文書全体の構造はピラミッドライティングを優先する。
- PREP法は段落単位で補助的に使う。
- 論点は `構造 / 記述 / 表記 / 運用` の4分類で整理する。
- 時系列記述は例外用途に限定する。
- `Decisions`, `Open Questions`, `Action Items` を明示的に分ける。
- TODO は未決事項と混在させず、担当者・期限・状態を持たせる。
- 表記ルールは Markdown を標準にして統一する。
- 箇条書きは `-` を基本とする。
- 日付表記は `YYYY-MM-DD` を基本とする。
- ステータス表記は `TODO / DOING / DONE / BLOCKED` を標準候補とする。

## Open Questions

- `Purpose` と `Summary` を見出し名として厳密に固定するか。
- `Summary` の推奨文字量や行数をどう定義するか。
- `Audience`, `Scope`, `Status` などの冒頭メタ情報を追加するか。
- 文書種別ごとにどこまでテンプレート差分を許すか。
- 見出し階層の深さをどこまで許容するか。
- 既存文書を新ルールへどう移行するか。
