# reference: パース仕様と既知の限界

`scripts/extract-keybindings.py` が各ソースファイルをどう解釈するかの正本。
スクリプトの実装を読まずに「この変更はパーサに影響するか」を判断するために使う。

## Hyprland (`user/hypr/hyprland.lua`)

- `local main = "SUPER"` からモディファイアキー名を取る。ハードコードせず、この行を読む。
- `hl.bind(` を起点に、括弧の対応を数えて呼び出し全体を1ブロックとして取り出す(1行・複数行どちらでも
  対応する)。
- ブロック内の `main .. "<combo文字列>"` からキー組み合わせ、`description = "..."` から動作名を取る。
  どちらか一方でも見つからない `hl.bind(...)` 呼び出しは「このパーサが理解しないバインド」として
  黙ってスキップする(例: `description` を持たない呼び出しが将来追加された場合)。
- `comma` → `,`、`semicolon` → `;`、`Return` → `Enter`、`mouse:272` → `マウス左ボタン`、
  `mouse:273` → `マウス右ボタン` の変換表を持つ。未知のキー名・マウスコードはそのまま生の値を表示する。
  新しいキーシム名(例 `period`, `BackSpace`)が出てきたら、この変換表に追記する判断は使う側(LLM)が行う。
- `--` で始まる行(Lua の行コメント)は解析前に空行へ置き換える。コメントアウトされた `hl.bind` は
  これにより除外される。

## foot (`user/hypr/foot.ini`)

- `[key-bindings]` セクションから次の `[...]` セクションまでの行を対象にする。
- `action=Combo` 形式の行を `=` で1回だけ分割する。
- 動作名の日本語訳は固定辞書 `FOOT_ACTION_DISPLAY` に持つ(現在4件: スクロールバック上下1行/1ページ)。
  辞書にない動作名は foot の生のアクション名をそのまま表示する(誤訳より原文優先)。

## qutebrowser (`user/browsers/qutebrowser.py`)

- 基本形: `config.bind('<key>', 'command')` または `config.bind('<key>', 'command', mode='...')` を
  直接正規表現で拾う。`mode` 省略時は qutebrowser のデフォルトである `normal` を補う。
- `for <var> in ['a', 'b', ...]:` という形のループを見つけ、そのインデントされた本体に
  `config.bind(..., mode=<var>)` がある場合、そのバインドのモードをリストの全要素を `/` で連結した
  表示に差し替える。対応するのはこの「文字列リストでループし、ループ変数をそのまま mode= に渡す」
  形だけで、他の動的な組み立て方(辞書のループ、関数での動的生成など)には対応していない。
- `map(key, command)` はこのファイル独自のヘルパー(`config.unbind` + `config.bind` の素通し)。
  スクリプトは `def map(key, command):` の本体を読み、`config.unbind(key)` と `config.bind(key, command)`
  がそのまま入っていることを確認したうえでのみ、`map(...)` の呼び出しを `config.bind` 相当として拾う。
  この確認に失敗したら(= `map` の実装が変わったら)、`map(...)` 呼び出しは一切抽出されなくなる。
  これは安全側の失敗(間違った内容を出すより、何も出さない方がよい)として意図的にそうしている。
- 既知の限界: 変数やf-stringでキー/コマンド文字列を組み立てている箇所、`config.bind` 以外の方法
  (例: 独自の別ヘルパー関数を新設する)で束縛する箇所は抽出されない。

## Neovim (`user/nvim/init.lua`)

- `--` で始まる行は解析前に空行へ置き換える(コメントアウトされた `vim.keymap.set` を除外する)。
- `vim.keymap.set(` を起点に括弧の対応を数えて呼び出し全体を取り出す。1行・複数行(関数リテラルの
  rhs を含む)のどちらにも対応する。
- 先頭2引数(mode, key)は必ずクォートされた文字列と仮定する。3引数目以降(rhs とオプション表)は
  まとめて正規表現の対象にし、`desc = "..."` があればそれを動作名として使う。
- `desc` がない場合:
  - rhs が `[[...]]` 形式の長括弧文字列、またはクォートされた文字列なら、その内容をバックティックで
    囲んで表示する。
  - rhs が無名関数(`function() ... end`)で `desc` も無い場合は `(無名関数、descなし)` と表示する。
    実際に Neovim を使う側が追う必要がある箇所なので、`desc` を足すことを推奨する旨は人間判断。
- モード略称(`n`, `i`, `v`, `x`, `t`, `c`)は固定辞書で日本語化する。未知の略称はそのまま表示する。

## fcitx5 (`user/fcitx5/*.conf`)

- 2026-10-03 時点で確認した `user/fcitx5/*.conf` 一式(`unicode.conf`, `punctuation.conf`,
  `chttrans.conf`, `pinyin.conf`, `waylandim.conf`, `spell.conf`, `hangul.conf`, `profile`,
  `classicui.conf`, `clipboard.conf`, `config`)にはキーバインド定義らしき行が見つからなかった。
  抽出対象に含めていない。
- 将来 fcitx5 側に明示的なキーバインド設定(例: 入力メソッド切り替えキーのカスタマイズ)が追加されたら、
  このファイルと `SKILL.md` の対象ファイル表、`scripts/extract-keybindings.py` の `SECTIONS` を
  見直す。

## 出力のレンダリング

- Markdown と HTML は同じ中間データ(`SECTIONS` ごとの行リスト)から、同じスクリプト内の純粋な
  文字列整形で作られる。LLM の介在なしに再生成できることが、このスキルの「ルールベースで
  トークン消費を抑える」という要件の核心。
- HTML はソースごとにセクション分けし、左にジャンプ用ナビ、キー表記は `<kbd>` で表示する
  固定テンプレート(`HTML_TEMPLATE`)を使う。デザインは初回作成時に決めたものをそのまま再利用し、
  再生成のたびにデザインを再検討しない。
