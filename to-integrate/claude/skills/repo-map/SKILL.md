# repo-map

一つのOSSリポジトリの**トップレベル全体**を、役割で緩やかにグルーピングした日本語リファレンスに整理する。

このスキルは `oss-repo-structure` と統合したものである（2026-09-26）。同じ作業に対して出力先と命名が3通り並存していた状態を、下記の「配置と命名」の1通りに決めた。

## 正典（必ず先に読む）

新規に書く前に既存の正典を**必ず読んで**、構成・語り口・粒度を合わせる。

- `silver-lake/dev/repo-structure.md` — Linuxカーネル。密度の基準はこれ。トップレベルの注釈付きツリーを先に置き、その後にMECE分類と、カテゴリごと・境界ごとの根拠を書く。

出力言語は**日本語**。指示（このSKILL）は英語混在で可。判断の規律は `logical-thinking` のMECE、表と図の体裁は `figure-rendering` と `technical-rendering` に従う。

## 成果物の節構成（この順で書く）

1. **タイトル** — `# <名前>リポジトリ ディレクトリ構成`
2. **TODOチェックリスト**（コードブロック）— 済んだ項目に `[x]`、次のステップ（サブディレクトリ深掘り等）を `[ ]` で残す
3. **導入ブロック引用** — リポジトリへのリンク、**基準コミット + 日付**、トップレベルの総数（`N ディレクトリ + M サブモジュール + K ファイル`）、そのプロジェクト特有の注意（例: 一次開発がGerrit/メーリングリストか等）
4. **目次**
5. **トップレベル全体のMECE構造** — グルーピングを1つのコードブロックで示す
6. **主要な兄弟間の境界線** — 混同しやすい兄弟がどこで線を引くかを箇条書き（`A vs B`: …）
7. **トップレベルディレクトリ一覧（役割）** — グループ順に、`ディレクトリ | 役割` の表。**全ディレクトリを漏れなく**
8. **サブモジュール（外部リポジトリ参照）** — `git ls-tree` で `commit` 型のエントリ。公開/非公開も添える
9. **トップレベルファイル群** — 種別ごと（ビルド / オーナーシップ・統制 / プリサブミット・CI / ライセンス・管理 / 静的解析・スタイル / VCS制御 …）に `ファイル | 役割` の表。**全ファイルを漏れなく**

深掘り（各ディレクトリのサブディレクトリ解説）は**次のステップ**。最初のパスはトップレベルの列挙とグルーピングで完結させ、TODOに残す。

## 手順

### 1. 権威ある一覧を取得する（treeless clone）

`api.github.com` はegressプロキシに塞がれている（403）。**gitで取る**のが確実。フルcloneは巨大なので、ツリーだけの遅延取得で軽量に済ませる。

```bash
cd "$SCRATCHPAD"   # 一時ディレクトリ（/tmp/claude-.../scratchpad）
git clone --depth=1 --filter=tree:0 --no-checkout https://github.com/<owner>/<repo>.git r
cd r
git ls-tree HEAD | awk '{print $2, $4}' | sort   # 型(blob/tree/commit)付きで全列挙
git log -1 --format='%H %ci'                       # 基準コミットと日付を記録
```

- clone先は**このリポジトリの外**（スクラッチ領域）にする。他プロジェクトのツリーをここに置かない。
- `--depth=1 --filter=tree:0` は必須。フルcloneは大規模リポジトリで数分とGB単位を費やす。
- `tree` = ディレクトリ、`blob` = ファイル、`commit` = **Gitサブモジュール**（別リポジトリ参照）。この3種を分けて数える。
- Bashの作業ディレクトリは呼び出し間でリセットされうる。**絶対パス**か、1コマンド内で `cd X && …` と連結する。

### 2. 完全に列挙し、数える

トップの全 `tree` / 全 `commit` / 全 `blob` を落とさず拾い、`N + M + K` を数えて導入と各節の整合を取る（表の行数と総数を一致させる）。

### 3. あいまいなエントリを実物で確認する

知らない/新しい/紛らわしいディレクトリは推測せず、遅延取得で中身を確認する。

```bash
git cat-file -p HEAD:<dir>/README.md   # READMEがあれば役割が一発で分かる
git ls-tree HEAD:<dir> | awk '{print $2,$4}' | head   # 中身の顔ぶれで判断
```

### 4. グルーピングの軸を決める（MECE）

そのプロジェクトの**支配的な構造軸**を1本選び、相互排他・完全網羅に割る。軸は1本だけ選ぶ。2本を混ぜると、あるエントリが2つのグループに入りうる状態になり、MECEが崩れる。

参考にする軸の例:

- **Linuxカーネル**: 実行フェーズ×資源ドメイン → `共通ライブラリ / 起動時実行 / 常時実行(吸収者=ハード差分吸収・制御者=資源ドメイン) / 開発支援`
- **Chromium**: レイヤードアーキテクチャ（下位は上位を知らない）→ `基盤 → OS/ハード抽象 → コアエンジン → 共有/拡張 → 製品(Embedder) / 外部参照 / 開発支援`

軸の見つけ方: 「下位ほど汎用・上位ほど製品」の依存の背骨、実行フェーズ、資源ドメイン、レイヤー分離線（"ここから製品/ここまで基盤"）を探す。最後に必ず `# 開発・ビルドの支援` グループを別立てにする（`build/` `tools/` `testing/` `docs/` `third_party/` 等）。

### 5. 兄弟の境界線を言語化する

「なぜ隣同士で別ディレクトリなのか」を、混同しやすいペアについて `A vs B`: A は〜、B は〜 の形で。ここが読者にとって一番価値が高い。

### 6. トップレベルファイルを分類する

ドットファイル含め全ファイルを機能で束ねる。定番の束: ビルドシステム / オーナーシップ・レビュー統制 / プリサブミット・CI / プロジェクト管理・ライセンス / 静的解析・コードスタイル / Git・ツール制御。

### 7. 配置と命名

- 保存先は `silver-lake/dev/<project>-repo-structure.md`。`<project>` はリポジトリ名を kebab-case にしたもの。
- 同じプロジェクトを扱う既存ノートがあれば、新規作成の前に名前を確認する。
- 成果物は**ソース**であってアーティファクトではない。`files-and-repository` の Artifact Output（`golden-mart/` にタイムスタンプ名で置く）は、その回だけの成果物のための規定なので、再利用されるリファレンスには適用しない。

以前は `data-lake/.../<SUBJECT>_REPO_DIRECTORY.md`（大文字スネーク）という指定もあったが、`files-and-repository` の kebab-case 規則に反し、その規則を強制する `guard-write.py` が書き込みを拒否する。正典として挙げられていた `LINUX_REPO_DIRECTORY.md` と `CHROMIUM_REPO_DIRECTORY.md` も、`data-lake/` が `.gitignore` 対象だったため現存しない。命名を上記に一本化した理由はこれである。

### 8. 記録

## 品質チェック

- [ ] 全 `tree` / `commit` / `blob` を列挙したか（表の行数 = 取得した総数）
- [ ] 基準コミットと日付を記録したか（再現性）
- [ ] ディレクトリ・サブモジュール・ファイルを**別々に**数えたか
- [ ] あいまいなディレクトリは実物で確認したか（推測で書いていないか）
- [ ] 兄弟の境界線を主要ペアで説明したか
- [ ] 開発支援グループを別立てにしたか
- [ ] 深掘りはTODOに残し、最初のパスはトップレベルで完結しているか

## MECE チェック

分類を確定する前に、次の3点を機械的に確かめる。

- **相互排他**: どのエントリも、入りうるグループが1つだけか。2つに入りうるなら軸が2本混ざっている。
- **完全網羅**: 列挙した総数と、全グループの要素数の合計が一致するか。
- **残余の明示**: どのグループにも入らないエントリを「その他」に投げていないか。投げるなら、なぜ軸に乗らないのかを書く。書けないなら軸の選び方が誤っている。
